# Redirect conversion tracking

Status: local candidate on `feature/redirects-dub-parity`. Apply the Redirects
workspace, policy and conversion migrations and deploy the handlers/proxy and
frontend together before using these endpoints. No production schema was changed
while implementing this phase.

## Connect a link

Open the managed link's **Link settings** and enable **Attribute leads and sales**.
GET visits receive a fresh `qg_click_id` in the destination URL, generated by the
atomic visit recorder. HEAD and expired fallbacks do not receive attribution IDs.
Incoming caller-supplied attribution IDs are removed before resolution.

The destination application should retain the last click in its attribution
session with a 30-day lifetime. The native queer.guide integration uses the
existing effective analytics-consent gate, including DNT and automation checks.
It removes the query parameter after a successful capture, clears stored
attribution on withdrawal, and aborts pending native attribution calls.

Confirmed native account creation is verified through `auth.getUser` on the
server. The caller cannot choose the customer ID or signup timestamp. A recorded
click must precede account creation and be within its 30-day attribution window.
Existing accounts cannot be credited as new signups from later clicks.

The existing Stripe donation flow carries the consented click into Checkout
metadata and a private donation attribution FK. Only verified paid events become
sale conversions. Paid asynchronous completion and renewals are supported. A
renewal retains the originating tracked checkout; untracked subscriptions are
not credited. Stripe purchase/invoice IDs make webhook retries idempotent.
Amounts use Stripe charge units, including zero/three-decimal currencies and the
ISK/UGX compatibility rules, before conversion to the report's major units.

## Server credentials

Create a credential in **Conversion setup**. The response shows its secret once.
Store it on your server. The database stores only a SHA-256 digest of a random
256-bit secret. Ordinary users cannot read credential metadata, and even admin
Data API reads cannot select token hashes. Admins can revoke credentials.

Credentials expire within one year and grant `conversions:write`, optionally
limited to selected managed link IDs. Scope, revocation and expiry are rechecked
inside the atomic conversion write, including after endpoint authentication.
These credentials cannot manage links or credentials.

## Lead and sale API

The branded base URL is `https://queer.guide/api/redirects`. The owned Supabase
handler is `/functions/v1/redirect-api`. Both use the same contract. Authenticate
with `Authorization: Bearer <server credential>`. Admin session JWTs can also
submit events. Regular user JWTs may only use the narrow native signup endpoint.

Send `POST /track/lead` with:

```json
{
  "clickId": "ACTUAL_RECORDED_CLICK_UUID",
  "customerExternalId": "CUSTOMER_ID",
  "eventId": "signup:CUSTOMER_ID",
  "eventName": "Sign up"
}
```

Send `POST /track/sale` with:

```json
{
  "customerExternalId": "CUSTOMER_ID",
  "eventId": "billing:INVOICE_ID",
  "eventName": "Purchase",
  "amount": "49.900000",
  "currency": "CHF"
}
```

A sale can resolve the customer's recorded attribution without another click ID.
For a direct purchase without a lead, include the recorded `clickId`. Customer
attribution anchors to the first accepted lead/direct sale and is not overwritten
by later explicit-click events. Native account customer IDs are `native:<user UUID>`;
use that namespace to connect custom server purchases to native signup leads.
Anonymous Stripe customers use Stripe customer IDs, or a session ID when Stripe
has no customer object. Customer IDs identify records, not deduplicated humans.

`amount` is in **major units**, unlike Stripe's minor units. Numbers and exact
decimal strings are accepted, with up to six decimal places and an upper bound
below 1 trillion. `currency` is an uppercase three-letter code. Reports preserve
decimal strings from PostgreSQL and accumulate micro-units as integers; they do
not combine currencies or apply exchange rates. Totals sum recorded sale amounts;
refund adjustments are not implemented in this candidate.

Use stable, globally namespaced `eventId` values across retries and credential
rotation. A repeated identical event returns the existing record. Reusing an ID
with different customer, click, kind, name, amount, currency, metadata, or an
explicitly different occurrence timestamp returns a conflict.

Optional fields: `metadata` (object, up to 8 KB) and `occurredAt` (timestamp, after
the click and no more than five minutes into the future). Requests are limited
to 64 KB. Lead events do not accept revenue fields.

Responses: `201` new event, `200` identical retry, `400` invalid event, `401` no
valid identity, `403` credential/scope denial, `404` missing attribution,
`409` conflicting event ID, `503` recording unavailable. Retry timeouts and
unavailability with the same event ID.

## Reports and verification

Visit reports show conversions attributed to the selected click-date cohort,
including later purchases, with revenue grouped by currency. Customer journeys
are private, chronological, cross-link and paginated. Historical click paths
remain unchanged after a slug edit. Native/lead/sale records also feed A/B winner
metrics without inflating click counts from joined conversions.

- `npm run test:redirect-sql`: isolated PostgreSQL migrations, RLS, credential
  metadata/hash access, scope/expiry/revocation, idempotency, customer anchors,
  exact revenue strings, historical paths, signup eligibility and pagination.
- `npm run test:redirect-stripe`: actual webhook source, real Stripe signatures
  and WebCrypto, isolated PostgreSQL, paid-only revenue, retry deduplication,
  renewals and experiment metrics. No provider requests or payments are made.
- Focused Vitest coverage includes the actual API/resolver/proxy sources,
  consent lifecycle, checkout request attribution, validation and report/setup UI.

Production provider delivery and browser sessions remain unverified. Full link
REST CRUD, SDK packages, outgoing webhooks, Segment/GTM, custom reports, live
streams, shared dashboards and identity enrichment remain separate ledger items.

## Private customer identity

Customer profiles attach optional name, email and public HTTPS avatar URL to an
existing recorded external customer ID. They are private to the workspace’s
current permitted analytics readers and do not enter public reports, events
exports or the redirect payload. An avatar loads anonymously without a referrer;
the backend never fetches its URL. Trusted applications can supply consented
identity explicitly; tracking a lead/sale does not automatically publish identity.

GET /customers/profile?id=<encoded external ID> requires events:read and a
visible visit/conversion. The response includes customerExternalId, name, email,
avatarUrl, version, updatedAt and canEdit. PATCH /customers/profile takes
customerExternalId, current version (null for first enrichment), and any identity
fields; empty text/null clears a field. A name is at most 120 characters, email
254 and avatar URL 2048. DELETE /customers/profile takes only customerExternalId
and version and clears identity while preserving events, attribution and a new
version. Stale edits, including stale drafts after clearing, return 409.

Writes require links:write plus events:read and edit authority over every link
attributed to the customer. Partial keys/members can read a visible customer and
only their scoped journey, but cannot change an identity shared with hidden links.
Viewers cannot edit, and current role/key/member/folder restrictions are checked
under the existing ACL lock. Customer attribution/profile changes serialize per
customer. Profiles live in a service-only RLS table; direct authenticated/anonymous
Data API access is denied. Deleting the original attribution anchor erases the
profile through FK cascade. A later explicit enrichment can re-anchor to a
remaining recorded conversion; old identity fields are not restored.

GET /customers/journey?id=<encoded external ID>&limit=50&cursor=<JSON {at,id}>
returns chronological scoped click/lead/sale pages. No caller can override link
scope. All five SDKs provide getCustomer/updateCustomer/clearCustomer/customerJourney
(or snake_case / Go names). The analytics activity table opens the profile/journey,
and the existing lead/sale panel uses the same account-scoped interface. Editing
prefills identity and captures its version; conflicts require discard/reload.
Clearing is explicitly confirmed and preserves the timeline. Account/customer
changes abort reads and reset drafts, and denied refreshes hide stale identity.

This flow is locally implemented and verified through migrated SQL, actual HTTP,
five native SDKs, UI races/conflicts and desktop/mobile browser fixtures. It still
requires controlled production schema/handler/frontend rollout.
